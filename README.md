# EchoMind

EchoMind is an AI-powered personalized education platform that leverages Generative AI to create dynamic, interactive, and tailored learning experiences. The platform generates personalized lesson plans, adaptive practice challenges, and comprehensive curriculums based on the user's mastery level, preferred language, and learning style.

## 🚀 Tech Stack

### Frontend
- **React 19**: Modern UI library for building responsive and interactive user interfaces.
- **Vite**: Ultra-fast frontend tooling and bundler.
- **Tailwind CSS**: Utility-first CSS framework for rapid and highly customizable styling.
- **Framer Motion**: For rich, fluid animations and micro-interactions.
- **Lucide React**: Beautiful and consistent icon set.

### Backend
- **Node.js & Express**: Fast and lightweight web server handling API routing and Server-Sent Events (SSE).
- **TypeScript**: End-to-end type safety across the entire stack.
- **Prisma**: Next-generation ORM for interacting with the database.
- **BullMQ**: Robust queue system for handling asynchronous background jobs (curriculum generation).

### AI & Services
- **Google GenAI (`@google/genai`)**: Powers the core intelligence, generating lesson plans, evaluating answers, and detecting misconceptions.
- **Google TTS API**: Generates realistic Text-to-Speech audio for lesson modules.

### Databases & Infrastructure
- **PostgreSQL (with pgvector)**: Primary relational database for storing user profiles and saved lessons.
- **Redis**: In-memory data structure store used for:
  - Caching TTS audio files to reduce latency and API costs.
  - Backing the BullMQ job queue.
  - Caching generated curriculums.
- **Docker & Docker Compose**: Containerized environment for easily spinning up Postgres and Redis locally.

## 🏗️ Architecture

EchoMind is structured as a monolith where a single Node.js/Express server serves both the frontend application (via Vite during development or statically in production) and the backend APIs.

### Key Architectural Patterns
1. **Server-Sent Events (SSE)**: Used for streaming AI-generated lesson plans (`/api/generate-lesson`). Since generating a full lesson takes time, SSE allows the frontend to progressively render modules as they are generated by the AI, providing a seamless and engaging UX without long loading spinners.
2. **Asynchronous Background Processing**: Heavy tasks like full curriculum generation (`/api/generate-curriculum`) are offloaded to **BullMQ**. The server immediately returns a Job ID, and the client polls the status until the job is completed. This prevents HTTP timeouts and frees up the main thread.
3. **Robust Fallbacks**: The system is designed with high-quality, hardcoded pedagogical fallbacks. If the Gemini API fails, times out, or the API key is missing, the backend seamlessly switches to fallback generators, ensuring the application remains usable.
4. **Caching Layer**: **Redis** is heavily utilized to cache Text-to-Speech (TTS) audio files and completed curriculum jobs, significantly reducing response times for repeated requests.

## 💾 Database Schema (Prisma)

- **User**: Stores user profiles, preferences (language, mastery level), and links to their saved lessons.
- **Lesson**: Stores the AI-generated lessons, including the topic, subject category, and the full JSON payload of the lesson modules.

## ⚖️ Trade-offs & Design Decisions

### 1. Monorepo / Monolith vs. Microservices
**Decision**: The app is built as a single repository with Express and React running together.
**Trade-off**: This simplifies development, deployment, and end-to-end type sharing. However, it tightly couples the frontend and backend. For a project of this scale, the simplicity and speed of a monolith far outweigh the scalability benefits of microservices.

### 2. BullMQ + Redis for Curriculum Generation
**Decision**: Offloading heavy AI tasks to a background queue.
**Trade-off**: Introduces Redis as a mandatory dependency and adds complexity to the frontend (which now must poll for job completion). However, this is necessary because generating a full multi-week curriculum via LLM often exceeds standard HTTP timeout limits (e.g., 30s-60s on most load balancers) and provides a much better user experience.

### 3. Server-Sent Events (SSE) vs. WebSockets
**Decision**: Using SSE for streaming AI responses.
**Trade-off**: SSE is unidirectional (Server -> Client), which is perfectly suited for streaming text generation. It is simpler to implement over standard HTTP than WebSockets, which require managing bidirectional persistent connections.

### 4. Deterministic Hashing for Caching
**Decision**: Using SHA-256 hashes of the payload (e.g., TTS scripts or curriculum requests) as cache keys in Redis.
**Trade-off**: Ensures that identical requests instantly return cached results, saving API costs and time. The downside is that if the AI needs to generate a *different* response for the exact same prompt (e.g., for variety), the cache will prevent it unless explicitly bypassed.

## 🛠️ Getting Started

### Prerequisites
- Node.js (v18+)
- Docker & Docker Compose (for Postgres and Redis)

### Installation

1. **Clone the repository and install dependencies:**
   ```bash
   npm install
   ```

2. **Set up Environment Variables:**
   Copy `.env.example` to `.env` and configure your keys:
   ```env
   GEMINI_API_KEY=your_gemini_api_key
   DATABASE_URL="postgresql://postgres:password@localhost:5432/echomind?schema=public"
   REDIS_URL="redis://localhost:6379"
   ```

3. **Start the Infrastructure (Postgres & Redis):**
   ```bash
   docker-compose up -d
   ```

4. **Initialize the Database:**
   ```bash
   npx prisma db push
   ```

5. **Start the Development Server:**
   ```bash
   npm run dev
   ```
   The app will be available at `http://localhost:3000`.
